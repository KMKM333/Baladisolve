# Supabase for Manāra — step 1

Everything the site shows lives in one HTML file today. This folder is the
database that will replace the arrays, without changing what the pages show.

## What is here

- `schema.sql` — the tables, with the same field names the site uses: requests,
  stage_events (the custody trail), verifiers, verifiers_l2, assignments,
  bids, pledges, milestones, evidence, variances, messages, affected,
  municipalities, and three public views that hide what must stay hidden
  (losing bidders' names, anonymous sponsors, the second line's identities).
- `policies.sql` — row-level security. Reads are public: the ledger is the
  product. Writes are narrow: your own profile, a pledge if you are a verified
  sponsor, a bid if you are a verified expert and the request is open, a
  message in a chat you belong to, joining an affected group. Every write that
  moves a request between stages is deliberately missing — that is step 2.
- `seed.sql` — the site's current data as inserts, generated by
  `node scripts/export-seed.mjs > supabase/seed.sql`. Regenerate it whenever
  index.html changes; never edit it by hand.

## Steps (yours, about twenty minutes)

1. Create a project at supabase.com. Pick the region closest to Beirut
   (Frankfurt). Keep the database password somewhere safe; it is not used by
   the site.
2. In the SQL editor, run `schema.sql`, then `policies.sql`, then `seed.sql`.
3. Authentication → Providers: leave Email on, turn on "magic link", turn off
   "confirm email" for the pilot. Residents never sign in; the four roles do.
4. Settings → API: copy the **Project URL** and the **anon public** key. The
   anon key is safe to publish — every table is protected by the policies.
5. In `index.html`, near the end, fill in:
   `window.MANARA_SUPABASE = { url: 'https://xxxx.supabase.co', anonKey: 'eyJ…' };`
   Until both are set the site runs on its built-in data. Once set, it loads
   requests, the custody trail, pledges and both chats from the database on
   every visit and falls back to the built-in data if the database is
   unreachable.
6. Commit and push. The daily Baladi sync keeps writing into index.html for
   now; pointing it at the requests table is the last part of this step and
   needs the service key, which stays in GitHub Actions secrets, never in the
   site.

## What happens next (step 2, when you say so)

The six stage transitions become database functions — certify, sign off,
confirm, choose a bid, capture, release — each checking who is calling and
what exists, and each writing its own stage_events row. At that point the
site stops being the keeper of the state and becomes a viewer of it.
